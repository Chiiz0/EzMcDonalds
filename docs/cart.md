# 查看、恢复加购并重新选餐

`cart_get(request)` 返回当前官方购物车、`cart_ref` 和 `cart_ref_expires_at`。配置加购成功也返回这些字段。引用有效120秒，绑定会员身份、门店、取餐时间与方式；只保存在本机，不是官方券号或购物车凭据。

已有餐品可先 `pickup_methods` 查看实际取餐方式，再 `checkout_quote`。门店只提供柜台自取或当前选择堂食时，不把它当作店内取餐柜；切换方式仍需官方 App，柜台自取付款适配尚未完成。用户要求移除原餐品或重新选餐时，个人 Agent 可以：

1. `cart_get` 查看餐品、份数、配料与金额，说明将移除哪些内容。
2. 使用同一 `request`、返回的 `cart_ref` 和这次操作固定的 `idempotency_key` 调用 `cart_clear`。
3. 确认返回 `cart_empty=true`，再用新的加购意图调用 `cart_add_configured`，最后重新报价。

`cart_clear` 会移除该购物车的全部餐品；目前没有逐行删除或原地改数量工具。不要为清除别人或用户在 App 中选好的餐品而擅自调用。这个工具不会取消已提交订单，也不会退款或付款。

## 加购断线与进程重启

加购前先查询实时商品，再以同一事务保存请求、商品选择、完整草稿及写入记录。发送后的响应或回读丢失，不会释放记录。重复同一 `cart_add_simple` / `cart_add_configured` 请求时直接核对原操作，不再重新查券、构造草稿或发送加购；原键对应的商品、门店、取餐时间、金额上限或工具种类变化会被拒绝。

丢失聊天上下文后调用 `cart_add_status(account)` 找回该会员最新一条项目加购记录，也可以传入原 `operation_id` 查询指定记录。CLI 对应：

```sh
ezmcd cart-status personal
ezmcd cart-status personal --operation-id "<返回的完整 operation_id>"
```

返回原请求和选择，以及当前购物车核对结果：

| state | 含义与后续动作 |
|---|---|
| `MATCHED` | 当前所有商品、数量、套餐组件、券及配料与原草稿相符；可继续获取新报价。价格仍需报价核对。 |
| `EMPTY` | 当前为空；不代表此前请求未执行，不能自动补加。 |
| `DIFFERENT` | 当前内容与原草稿不同；展示当前与原选择供核对，不恢复旧内容。 |
| `UNAVAILABLE` | 本次无法读取或验证购物车；原选择仍可找回，按 query_error 处理登录、时段或网络问题后继续查询。 |

`write_receipt_verified` 表示是否收到并校验过原加购成功响应；`cart_matches_requested` 只表示当前内容相符，不能证明是哪一个客户端完成了加购。`ever_matched` 是历史证据，不能替代本次 state。`add_attempted=false` 表示这次恢复没有再次尝试发送；所有结果均不创建订单或付款。

本账号有从未核对成功的加购时，新键也不能绕过它。先查询；只有用户确实决定重新选餐，才检查原门店/时段的购物车并显式清空，确认空车后开始新操作。清空不会取消已发送的服务端请求，也不是网络异常的自动重试方案。不要并发编辑。已经核对成功的旧请求在餐品被移除后仍只报告 `EMPTY`，不会恢复旧餐品。

查询范围限本项目 a14 起保存的记录，不包括官方 App 操作。旧版只有写入回执、缺少原草稿，保持只查询，不猜测补建。登录失效或本地撤销后仍可显示已保存选择，但实时核对会标记 `UNAVAILABLE`；已过取餐时间的记录也不会自动改成今天。最新记录不是完整历史列表。

## 防止重复与误清空

清空前重新读取完整服务端购物车，比较餐品、份数、配料、券和金额等字段，只排除服务端时钟。内容或范围变化、引用过期时停止，不自动换一个新引用再次清空。空购物车直接确认，不发送写请求。

非空车只发送一次官方 `PUT /bff/cart/carts/empty`。账号锁与 SQLite 事务在网络发送前绑定引用、幂等键和写入记录；随后回读确认空车。成功或超时后，同一引用和键再次调用都只读查询，即使进程重启或后来添加了其他餐品，也不再次清空。

- `clear_attempted`：本次调用是否发送了清空请求。
- `cart_empty`：本次回读是否为空，不表示原清空请求一定成功。
- `original_clear_verified`：原操作是否曾通过空车回读核验。
- `repeated`：是否在查询已尝试的同一操作。

未知结果先 `cart_get` 或用原引用和原键查询。不得为了重试换键。新的改餐意图需要重新查看、取得新引用并使用新键。查询旧操作时，即使 `original_clear_verified=true`，当前购物车仍可能已有新餐品。

同一账号的项目调用受本机锁保护；官方 App 和其他设备不受该锁控制。已观察到的接口没有条件版本更新参数，读取与清空之间仍存在外部并发窗口，不能声称跨客户端原子操作。改餐期间不要同时在其他入口编辑购物车。

## 实际验证范围

已通过真实 stdio MCP：普通冰美式券、少冰选项、加购回读、¥9.90 报价、清空回读及重复调用只查询。服务端把少冰选项回显为 `customization.items`，确认页把配料描述放在 `comboItemList`；项目分别核对结构化选择和确认页名称、份数，没有把缺少商品代码的行一概忽略。

测试结束后购物车为空，优惠券剩余次数、官方订单列表、钱包余额、账号与偏好文件不变，消费保持关闭。普通券付款和其他商品的改餐流程未因此获得真实支付验收。

a14 在真实咖啡券购物车上由本地测试工具故意丢弃成功响应和首次回读，首次结果为 `UNAVAILABLE`，换键请求被拒绝。新 MCP 进程找回原选择并得到 `MATCHED`，重复原请求不重建草稿、只查询，报价仍为¥9.90；清空后再次调用原请求报告 `EMPTY`。加购和清空各发送一次，订单、余额及券次数未变化。这是本地故障注入测试，不是声称遇到并复现了真实网络故障。

a15 实测普通单品多份及多品：两份脆薯饼、脆薯饼＋脆香油条分别加购、报价¥17.00并清空。普通商品购物车省略原价小计时，仅对无券、无配料、原价等于现价的已验证结构按单价×数量计算，再与确认页逐行及整单核对。缺字段、冲突及其他结构仍停止。

另一门店的两份脆薯饼加购核对通过，但确认页只提供堂食和柜台自取，因此没有形成可付款报价。该轮草稿也已清空。各轮独立核对订单、钱包、账号与偏好不变；真实购买仍只有原早餐卡消费验收。
