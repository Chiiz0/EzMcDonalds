# 商品与套餐选择

先选门店、实际可用时段，再调用 `menu_list`。同款商品可能有普通价和权益卡报价，使用返回的 `offer_id` 选择具体优惠。过期优惠不会被历史 ID 替代。

`product_detail` 是只读工具。虽然官方接口使用 POST，它只读取详情，不修改购物车、创建订单或付款。返回套餐的 `groups`：每轮的 `round`、可选组件、数量上下限、加价和 `standard_configuration_supported`。

例如，实时详情假设给出了商品 `900001`、主食轮次 1 与饮品轮次 2，选择结构如下。这里的代码是虚构示例，实际调用应复制当前返回值。

```json
{
  "product_code": "900001",
  "offer_id": "copy-from-live-menu",
  "quantity": 1,
  "combo": [
    {"round": 1, "items": [{"product_code": "100001", "quantity": 1}]},
    {"round": 2, "items": [{"product_code": "200002", "quantity": 1}]}
  ]
}
```

把选择作为 `items` 传给 `cart_add_configured`，同时提供 `request` 和本次加购稳定的 `idempotency_key`。所有轮次必须明确选择一次，不能把其他轮次的商品填进来。工具重新查询菜单和详情，校验库存、份数、组件和实时优惠标识，然后对空购物车发送一次加购。

可选轮次的 `min_quantity=0` 时，可显式传入该轮的 `items: []`。必选轮次不能用空列表跳过；加购前会重新检查实时限制。

首次加购遇到非空购物车时会停止；可直接报价已有购物车，或按用户改餐意图先 `cart_get` 查看，再用返回的短期引用调用 `cart_clear`，确认空车后重新选餐。重复原请求只核对已保存草稿；加购未知结果或丢失聊天上下文时用 `cart_add_status` 找回原选择，不能换 key 重复加购。只有 `MATCHED` 才建议继续报价。加购成功也不等于价格已获认可，必须再调用 `checkout_quote`。[改餐与清空说明](cart.md)。

当前脚本配置覆盖 type=1 单品、type=7 套餐、已观察到的默认简单配料、免费保留/去除与单选配料（例如冰量），以及 `optional_choice` 标记的可选换奶等二选项。其他收费配料、冰量结构和高级定制尚未完整适配，详情中的支持标记会说明可选范围。复杂商品仍可在官方 App 配好，再由本项目读取、报价和提交支持的购物车；未识别的商品类型、费用或优惠会停止。指定单品券的流程见[优惠券选择](coupons.md)。

已完成原组合真实加购、早餐卡报价和套餐详情读取；普通冰美式券加少冰的真实加购、回读、¥9.90报价与清空也已通过。更多配料及组合仍需真实验收；本轮没有新增订单或扣费。

## 配料保留与去除

`product_detail` 的顶层和每个套餐组件均提供 `modifiers`。当 `supported=true` 且存在可选组时，按返回的代码在商品或该组件上添加：

```json
"modifiers": [
  {"code": "从详情复制的奶油球代码", "quantity": 1},
  {"code": "从详情复制的白砂糖代码", "quantity": 0}
]
```

实际代码必须是接口返回的数字字符串。传入 `modifiers` 时需要逐项明确全部活动组的代码，不能漏项；保留/去除组使用0或1，不传 key。不传 `modifiers` 时采用支持范围内的官方默认值。套餐配料放在对应组件上，不能放在套餐顶层。

`kind=single_choice` 的冰量等组使用一条 `{"code":"从详情复制的代码","quantity":1,"key":"从所选项复制的key"}`，只选一个免费、可用的选项。同一组所有选项的 code 相同，key 用于区分标准、去冰或少冰，不可凭名称猜 key。`inactive=true` 的整组售罄且没有默认选项时不提交该组；不能主动选择其中选项。收费或其他结构不会猜测。

`kind=optional_choice` 使用 `{"code":"从详情复制的代码","quantity":1}` 选择，`quantity=0` 不选择，不填写 `key`。目前支持默认不选、可选一项的已观察结构；`extra_cny` 是选中时每份商品的附加费，`selection_supported` 与 `available` 都应通过。脚本保存当时的配料选择和费用，回读后若选项或费用不同便停止；这份本地费用证据不会发送给官方接口。

服务端可能在“不换奶”回显里仍列出可选费用，但所选数量为0；这不产生加价，也不要求确认页出现换奶标签。选择换奶时则必须核对加价标签、原价加附加费、实际单价、份数及行金额。真实 MCP 已验证卡布奇诺中杯：不换奶¥21、换燕麦奶¥23；¥22上限拒绝后者，重启不重加，测试车已清空。没有为此创建或支付订单。

项目按实时详情重新校验、仅发送一次加购，然后读取购物车核对所有修改。未回显、被改回默认或出现额外商品时，加购状态为 `DIFFERENT`，Agent 应停止并核对，不重试、不直接付款。单品配料也进入报价内容指纹，报价后发生变动需重新确认。

## 规格聚合商品

`type=3` 代表规格选择入口，详情返回 `specifications` 和 `variants`。每个规格附带当前菜单中对应的 `menu_offers`；优先选择具体商品自己的菜单优惠，再读一次 `product_detail` 继续配置。

部分规格只出现在详情页。若其 `parent_detail_selection` 非空，可将其中的 `product_code`、`variant_of`、`offer_id` 原样传给 `product_detail`；确认后，连同数量、可选配料一起传给 `cart_add_configured`。这里 `variant_of` 是父商品代码，`offer_id` 是已验证的父菜单入口，不能省略或改用其他优惠入口。例如：

```json
{
  "product_code": "100001",
  "variant_of": "G900",
  "offer_id": "copy-from-parent-detail-selection",
  "quantity": 1
}
```

以上仍为虚构代码；实际选择必须来自实时返回值。加购前会重新核对父商品、规格维度及组合唯一性、子商品库存、配置和数量限制。当前这条路径支持普通单品及详情中完整给出轮次、选项和已识别价格公式的普通套餐规格；另有以下受限的咖啡卡路径。未识别的优惠或组合结构仍需自己的菜单入口或官方 App 配置，不会退回原价。

咖啡卡父页规格只有在以下实时证据一致时才返回选择入口：菜单卡与本人可用券的完整身份、所选门店/时间的资格、两份适用商品代码列表及卡商品接口、父页该规格对应的同一卡促销、规格原价与库存。当前仅支持已观察的非预付、单品任选卡结构；不支持推导其他条件券或促销套餐。加购前重新读取，卡的当日/总剩余次数、商品/促销上限都适用，多行同卡或同规格不能绕过限额。

验证后的规格返回 `pricing_source=verified_card_variant`、实际卡名称、`display_price_cny` 优惠展示价及 `regular_display_price_cny` 原价；最终仍以购物车和确认页报价为准。真实样本中咖啡卡中杯燕麦奶铁适用¥9.90，大杯虽在同一父页却不适用，不能继承中杯优惠。默认标准冰的结构保留在报价内容中；官方确认页未展示该默认标签时，仅接受已观察的免费标准冰字段，缺失的自定义选项仍拒绝。

套餐规格需要继续选择每个 `groups` 轮次，再把 `combo` 一起传给 `cart_add_configured`。`specification_choices` 给出规格组与选项的名称、代码，例如“规格 → 配现磨美式”；不能仅凭相同的套餐名称猜是哪一种规格。

`display_price_cny` 可能已经包含默认饮品的加价；`configuration_base_cny` 是经过公式和默认份数核对的套餐起价，`default_components_extra_cny` 是展示价里已包含的默认加价。选餐方案从起价加所选组件差价进行预估，避免重复计算。实际报价仍以购物车和确认页为准。已观察到的无折扣套餐可能把购物车 `originPrice` 写为0、同时省略 `subTotalPrice`；项目只在实际单价、份数、行金额、组件与确认页一致时接受此结构，不将0当作免费商品或忽略金额差异。

详情可能推荐第二杯等关联优惠。`optional_promotions_present=true` 只说明存在推荐，不代表已经选择；项目不会自动添加关联商品或促销 ID。规格展示价也不等于结算价，必须重新报价，并遵守用户预算及本地消费策略。

真实验证已覆盖一个未单独列在菜单的“热牛奶大杯”：父页选规格、加购回读、¥23.00报价、¥20上限拒绝、重启后原请求不重复加购，以及最终清空。没有购买或扣款；这不代表所有规格及关联优惠已验收。
