# 商品与套餐选择

先选门店、实际可用时段，再调用 `menu_list`。同款商品可能有普通价和权益卡报价，使用返回的 `offer_id` 选择具体优惠。过期优惠不会被历史 ID 替代。

`product_detail` 是只读工具。虽然官方接口使用 POST，它只读取详情，不修改购物车、创建订单或付款。返回套餐的 `groups`：每轮的 `round`、可选组件、数量上下限、加价和 `standard_configuration_supported`。

例如，实时详情假设给出了商品 `900001`、主食轮次 1 与饮品轮次 2，选择结构如下。这里的代码是虚构示例，实际调用应复制当前返回值。

```json
{
  "product_code": "900001",
  "offer_id": "copy-from-live-menu",
  "quantity": 1,
  "combo": [
    {"round": 1, "items": [{"product_code": "100001", "quantity": 1}]},
    {"round": 2, "items": [{"product_code": "200002", "quantity": 1}]}
  ]
}
```

把选择作为 `items` 传给 `cart_add_configured`，同时提供 `request` 和本次加购稳定的 `idempotency_key`。所有轮次必须明确选择一次，不能把其他轮次的商品填进来。工具重新查询菜单和详情，校验库存、份数、组件和实时优惠标识，然后对空购物车发送一次加购。

购物车非空时会停止；可直接报价已有购物车，或由用户在官方 App 处理原有内容。加购未知结果时先 `cart_get` 查看，不能换 key 重复加购。加购成功也不等于价格已获认可，必须再调用 `checkout_quote`。

当前脚本配置覆盖 type=1 单品、type=7 套餐、已观察到的默认简单配料，以及详情标记支持的免费保留/去除配料。收费配料、复杂冰量/换奶和其他高级定制尚未完整适配，详情中的支持标记会说明可选范围。复杂商品仍可在官方 App 配好，再由本项目读取、报价和提交支持的购物车；未识别的商品类型、费用或优惠会停止。

已完成原组合真实加购、早餐卡报价和套餐详情读取；新增配料修改与更多组合仍需真实写入验收。没有为了开发这一功能新增订单或扣费。

## 配料保留与去除

`product_detail` 的顶层和每个套餐组件均提供 `modifiers`。当 `supported=true` 且存在可选组时，按返回的代码在商品或该组件上添加：

```json
"modifiers": [
  {"code": "从详情复制的奶油球代码", "quantity": 1},
  {"code": "从详情复制的白砂糖代码", "quantity": 0}
]
```

实际代码必须是接口返回的数字字符串。传入 `modifiers` 时需要逐项明确全部代码，不能漏项；0 表示去除，1 表示保留。不传时采用支持范围内的官方默认值。当前只适配免费、0/1 数量及已核对 key 结构，收费或其他结构不会猜测。套餐配料放在对应组件上，不能放在套餐顶层。

项目按实时详情重新校验、仅发送一次加购，然后读取购物车核对所有修改。未回显或被改回默认时返回 `cart_modifier_selection_not_confirmed_review_cart`，Agent 应停止并核对，不重试、不直接付款。单品配料也进入报价内容指纹，报价后发生变动需重新确认。

## 规格聚合商品

`type=3` 代表规格选择入口，详情返回 `specifications` 和 `variants`。每个规格附带当前菜单中对应的 `menu_offers`；选择其中具体的商品代码与优惠后，再读一次 `product_detail` 继续配置。没有匹配菜单项时交回官方 App，不将聚合入口当作可直接下单商品，也不把一种规格的卡优惠套给另一种。
