# 从偏好到选餐方案

用户可通过个人 Agent 调用 `preferences_save`，保存店铺、餐品名称、饮品等套餐组件、数量、星期、取餐时间和金额上限。偏好只存在本机，不改变消费策略，也不创建定时任务。可用 `preferences_get` 查看。

## 一次选择，之后复用

1. `stores_search` 使用城市和关键词查店，或使用用户明确提供的经纬度查附近店；返回分页结果、地址、营业时间。不会擅自获取位置。
2. `pickup_slots` 返回北京时间的具体可预约时间，已过去的时间会过滤；门店营业不代表任意时刻都能自取。
3. `menu_list` 返回菜单分类、图片、展示价格和卡优惠；也可用 `coupons_list → coupon_products` 选择当时可用的单品券。`product_detail` 返回套餐各轮可选组件和配料。
4. `preferences_save` 保存用户选定的名称和条件；账号可以暂不绑定，之后 `meal_plan` 显式传入账号。
5. `meal_plan` 先检查目标账号、门店、取餐时间是否已有本地购买记录。有则交回原尝试；没有才从当前可预约时段中选择符合偏好的下一次时间，再检查该时间的购买记录，然后读取菜单、优惠和详情，输出 `CheckoutInput` 与 `ItemSelection` 草案。

`meal_plan` 不加购、不下单、不付款。指定 `date` 时只检查这一天，不会悄悄改到其他日期；不指定时在官方当前开放的预约范围内查找。星期以北京时间计算，0 表示周一、6 表示周日。

## 同一餐已经下过单

`existing_purchase=true` 表示该账号、门店、取餐时间已有本地购买记录。此时 `selection_ready=false`、`quote_required=false`、`items=[]`，`existing_orders` 提供原尝试、原餐品、金额和下一步。Agent 应核对原记录，按其中的 `attempt_id` 调用 `order_status`；没有订单号的未知尝试可用 `official_orders_list` / `official_order_detail` 查看候选，或在官方 App 核对，不能换 key 再买。

该检查发生在联网之前，因此账号退出、会话过期或刷新未完成时仍能找回。明确传入过去日期也可恢复该餐，即使偏好的星期已经改变。不传日期则先检查下一次未来的偏好星期和时间，不会用昨天的早餐替代下一餐；门店实际可预约日期仍以实时接口为准。

已经付款、尚未付款、结果不明和已取消均保留原记录。更换餐品、预算或柜台/取餐柜偏好不会把相同门店和时间变成新订单；返回的金额及餐品属于原记录，不会用新偏好覆盖。

这是本地日志快照，`live_status_checked=false`；不代表刚验证过付款，也不包含只在官方 App 中创建的订单。后续查询仍需要有效会话。返回没有记录也不替代提交前的实时订单检查、账号锁和防重复约束。

## 匹配规则

- 按餐品完整名称匹配；名称相同但商品不同，需要明确选择。
- 菜单中的商品组入口不作为可直接购买的套餐。
- 普通单品、已支持套餐或咖啡卡规格只出现在详情时，可保存 `items[].variant_of` 为父商品的完整名称、`name` 为具体规格完整名称。同名规格用 `variant_specifications` 明确分组和选项，例如 `{"规格":"配现磨美式"}`；仍有多个匹配或名称消失时停止。每次计划重新解析父入口和规格，传给加购的是实时代码。此模式不能与 `coupon_name` 混用，不自动选择关联推荐。`require_card_discount=false` 选择普通父入口，`true` 仅选择经实时卡资格、适用商品及对应促销共同核验的卡规格；不能匹配时停止。具体字段见[商品选择](products.md)。
- 套餐规格仍需按名称指定饮品等多选项轮次。预估使用已核对的起价加所选组件差价，不把展示价中包含的默认加价再算一次；最终仍需实时结算报价。
- 同一商品有多个报价入口且展示价格均已知时，选择最低展示价；最终金额仍以结算为准。
- `require_card_discount=true` 时只选择有卡优惠的入口，缺卡优惠时停止，不自动改成原价。
- 设置 `items[].coupon_name` 时按券的完整名称重新查询，再匹配该券下的商品；失效、同名多张或不支持的券会停止，不回退普通菜单。显式单品券与 `require_card_discount=true` 冲突，不假设两种优惠可以叠加。
- 用户指定的饮品必须在该轮可用且支持当前配置；不会自动替换成其他饮品。
- 必选轮次只有唯一选项时可以补齐；存在多个选项却没有偏好时返回待选择项。
- 可选轮次允许明确选择空列表；后续加购仍按实时最少数量校验。
- 套餐组件加价和份数纳入估算；已知估算超限即停止。展示价或估算不等于最终报价。
- 不支持的定制、缺货、名称歧义或时段不可用会返回结构化 `issues`，不会返回可直接执行的半份购物车草案。

## 记住配料偏好

先读取 `product_detail`，使用其中标记支持的配料完整名称。单品的配料偏好放在 `modifiers`；套餐放在对应的 `component_modifiers`，例如：

```json
{
  "name": "从菜单复制的套餐名称",
  "component_names": ["从详情复制的咖啡名称"],
  "component_modifiers": [{
    "component_name": "从详情复制的咖啡名称",
    "modifiers": [{"name": "从详情复制的糖包名称", "quantity": 0}]
  }]
}
```

这是 `preferences_save.preferences.items` 中的一项。对于保留/去除配料，`quantity=0` 去除、`1` 保留；未指定的其他配料沿用本次官方详情的默认值。方案会重新按名称找到当前代码并补齐全部配料选择，不保存可失效的配料代码。

对于冰量等 `single_choice` 组，指定一个选项名称且 `quantity=1`；例如 `{"name":"少冰","quantity":1,"group_name":"冰(单选)"}`，组名和选项必须复制当前详情。`group_name` 可区分不同组的同名选项。选择少冰会替换该组默认选项，实时解析其 key；去冰同样应选“去冰”并设为1，而不是把数量设为0。

要求的配料找不到、同名选项不唯一、选择违反实时数量限制、选项售罄或该组件没有被选中时，方案会返回问题并停止。不会把“不加糖”忽略掉，也不会因为设置配料就额外加入另一杯饮品。少冰单选已完成真实加购、报价和清空；未识别的定制仍交回官方 App。

已支持的 `optional_choice` 可按名称保存，例如 `{"name":"换燕麦奶","quantity":1}`。预估按实时附加费及商品/组件份数计入总额，超过预算时停止；不选或明确设为0时不计该费用。卡布奇诺换燕麦奶的¥23方案与真实报价一致，¥22偏好上限会拒绝；没有开启消费权限或改变默认早餐。其他收费结构及套餐内收费选项尚未完成实机验收。

## 记住指定优惠券

在同一条商品偏好上增加 `coupon_name`，名称来自当前 `coupons_list`，商品名称来自其 `coupon_products`。早餐卡仍走菜单中的卡优惠入口。项目不保存券的原始 ID，下一次方案重新检查账号、门店、时段、剩余次数及商品详情。券的展示价不能替代最终结算，更多限制见[优惠券选择](coupons.md)。

## Agent 执行顺序

先调用 `meal_plan`。若返回 `existing_purchase=true`，按 `existing_orders` 核对原尝试，不再加购或提交。否则继续 `cart_get → cart_add_configured（购物车为空时）→ checkout_quote → checkout_submit → order_status`。

使用方案提供的稳定 `idempotency_key`，同一次购买不要反复生成新 key。已有购物车先核对，不覆盖。`selection_ready=true` 只说明选餐草案完整，不代表已经授权消费或具备下单运行字段。

## 本地 CLI

```sh
ezmcd preferences show
ezmcd preferences save --file /absolute/path/preferences.json
ezmcd preferences plan --account personal
ezmcd preferences plan --account personal --date 2026-11-02
```

JSON 文件权限需为 0600。日期仅为格式示例；可预约时间取自实时接口。自动调度由用户另行设置，本项目不会因为偏好选择“每天”就开始购买。
